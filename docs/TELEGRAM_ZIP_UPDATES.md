# Telegram ZIP updates

`/update` is disabled by default. An authorized administrator opens a short-lived, single-upload window before sending a ZIP. The bot stages the ZIP for review; it never writes into the running checkout. Production activation is a separate action through the optional, disabled-by-default systemd deployment broker.

## Upload, review, and approval

1. In `ADMIN_CHAT_ID`, a user in `ADMIN_USER_IDS` (or the separately configured `ADMIN_ID`) runs `/update enable`. This opens one upload slot for `UPDATE_UPLOAD_WINDOW_SECONDS` (default 300; allowed 30–900 seconds). `/update status` reports state; `/update disable` closes an unused window; `/update cancel` closes it when no upload is processing. `/update` without a subcommand displays usage. ZIP uploads are rejected by default, including uploads from unauthorized users.
2. The window state is stored in the application SQLite database. A single conditional transaction reserves the slot before download, preventing simultaneous or duplicate uploads; success and failure both close it. Expired or interrupted processing state is closed during startup recovery. If persistent gate state cannot be read or changed, the upload is refused. This permission only permits one ZIP to enter staging; it does not approve deployment.
3. The bot enforces `MAX_UPLOAD_BYTES`, places the upload in a private quarantine directory, and requires a successful ClamAV scan even when general upload scanning is disabled. A malware result, scanner error, or timeout fails closed. Failed scan/validation archives remain in quarantine for administrator follow-up and expire during cleanup.
4. The staged manager validates the archive and protected paths, computes SHA-256 hashes and a deterministic release manifest, and extracts to an isolated staging directory. ZIP inspection and extraction are bounded by `UPDATE_EXTRACT_TIMEOUT_SECONDS`.
5. Python syntax checks run against the staged files. The project test suite must also pass in the configured rootless Docker sandbox. If the sandbox is disabled or unavailable, tests are marked `BLOCKED`; the bot does not claim a pass and staging approval is refused.
6. Review the bot's preview, including the release digest, file actions, security notes, syntax status, and isolated-test result. `Approve staging only`, `Reject`, and `Cancel` apply to that exact digest. A changed artifact invalidates a callback. Review data and approvals are process-local and expire after 30 minutes; a bot restart clears the active review state.
7. The separate `Approve production deployment` action submits the same update ID, manifest SHA-256, archive SHA-256, and fixed deploy operation to the broker. By default, the request remains pending and a root operator must run `sudo /usr/local/libexec/telegram-ai-deploy --authorize <UPDATE_ID>` from an interactive terminal, verify the actual admin approval in Telegram, and confirm the full digest. A root operator may instead configure the broker process with `TELEGRAM_AI_AUTO_DEPLOY_ADMIN_IDS` (a comma-separated allowlist of Telegram admin IDs). Only when the callback admin ID is in that broker allowlist does the broker consume the matching request and queue activation automatically. The upload-window command and staging approval never authorize production deployment. Broker authorization expires after 15 minutes, is one-time, and is stored in root-private state. An unset or empty allowlist preserves manual root approval; the installer leaves the broker socket disabled.

With the root-owned auto-deploy allowlist configured, the separate production callback authorizes only the exact reviewed digest and the broker performs its existing validation, backup, activation, restart, health-check, and rollback flow. Without that explicit root-side policy, interactive root approval remains required. The broker must run on the same compatible Linux VM as the bot and its configured local socket/staging paths; there is no remote SSH/SFTP transfer.

Every command, upload, and callback is restricted to configured administrators and the administrator chat. The bot audits gate/staging and approval decisions without recording secret values.

## What can be deployed

The review package may include application source, tests, and documentation for inspection. The broker activates only permitted `src/enan_ultra/` files. It rejects dependencies, database migrations, protected update/security/runtime control files, and persistent-state paths. An uploaded ZIP is a patch: files it omits are retained from the running allowlisted source tree, and ZIP uploads do not delete files. `.env`, database files and SQLite sidecars, uploads, stickers, backups, and runtime state are outside the release tree and remain untouched.

The bot socket request cannot choose arbitrary paths, commands, or a release operation; it submits only the fixed deployment request. With no root-side auto-deploy allowlist, it creates a root-owned pending request and only root-only `approval_details` and `authorize` operations can consume it. If the root-owned `TELEGRAM_AI_AUTO_DEPLOY_ADMIN_IDS` allowlist is nonempty, the broker may instead consume a request only when its claimed admin ID exactly matches that allowlist. Both modes require a pending, unexpired request and bind authorization to the full manifest and archive digests. Auto mode trusts the bot service process to report the Telegram callback identity correctly; compromise of that service account could forge an allowlisted claim and request deployment of a broker-acceptable staged release. Enable auto mode only if that expanded trust boundary is acceptable, keep the allowlist minimal, and retain distinct staging and production approvals.

The broker builds an immutable directory under `/opt/enan-ultra/releases/<digest>/`, verifies its files against the approved manifest, then atomically switches `/opt/enan-ultra/current`. It restarts only `telegram-ai.service`. A fresh PID-bound health marker must report the active release import origin, an open database, and the same Telegram bot identity. If the candidate fails, the broker switches back to the verified prior release and checks it again. `rollback_failed` means recovery was not verified and needs manual host-side recovery.

This broker layout is a local design for `telegram-ai.service`, user/group `enan-ultra`, and `/opt/enan-ultra`. The historical Azure target in the readiness report was a different service and path; its current identity has not been independently rechecked. Do not enable the broker on a host until its target, ownership, service unit, state paths, and recovery process have been verified there.

## Configuration names

Bot settings include `ADMIN_ID`, `ADMIN_CHAT_ID`, `ADMIN_USER_IDS`, `UPDATE_UPLOAD_WINDOW_SECONDS` (default 300, range 30–900), `MALWARE_SCAN_ENABLED`, `CLAMAV_SOCKET_PATH`, `CLAMAV_SCAN_TIMEOUT_SECONDS`, `MAX_UPLOAD_BYTES`, `MAX_ARCHIVE_EXPANDED_BYTES`, `UPDATE_MAX_FILES`, `UPDATE_MAX_DEPTH`, `UPDATE_MAX_PATH_LENGTH`, `UPDATE_MAX_COMPRESSION_RATIO`, `UPDATE_EXTRACT_TIMEOUT_SECONDS`, `UPDATE_TEST_TIMEOUT_SECONDS`, `CODE_SANDBOX_ENABLED`, `CODE_SANDBOX_IMAGE`, `CODE_SANDBOX_TIMEOUT_SECONDS`, `CODE_SANDBOX_MEMORY_MB`, `CODE_SANDBOX_CPU_COUNT`, `CODE_SANDBOX_MAX_FILES`, `CODE_SANDBOX_MAX_EXPANDED_BYTES`, `UPDATE_DEPLOYMENT_ENABLED`, and `UPDATE_DEPLOYMENT_SOCKET_PATH`. `TELEGRAM_AI_AUTO_DEPLOY_ADMIN_IDS` is read only by the root broker process and defaults to an empty allowlist; do not put it only in the bot `.env`. See `.env.example` and [configuration](./CONFIGURATION.md) for bot settings and defaults.
