# Telegram ZIP update security

Telegram ZIP updates are a privileged code-release path. `/update` stages and reviews code; it never overlays the running application or restarts the bot directly. A separate production approval can request activation only through the fixed, root-owned deployment broker. Keep the broker disabled until the real target and rollback process have been verified.

## Identity and upload handling

- Upload controls, uploads, and callbacks accept only IDs in `ADMIN_USER_IDS` plus the separately configured `ADMIN_ID` (or its documented legacy fallback). They must also come from `ADMIN_CHAT_ID`. Other bot users cannot submit ZIPs, and general admin status alone does not grant deployment authority.
- ZIP upload is disabled unless `/update enable` opens a single-use window. `UPDATE_UPLOAD_WINDOW_SECONDS` defaults to 300 seconds and is limited to 30–900 seconds. SQLite stores the gate state; an atomic claim permits one concurrent upload, and success/failure closes the gate. Expired windows and interrupted processing are closed at startup. A database error or invalid state fails closed.
- The upload is size-limited, placed in a private quarantine directory, scanned by ClamAV, then validated and hashed before staging. ZIP updates require a clean scan regardless of `MALWARE_SCAN_ENABLED`; scanner unavailability, timeout, invalid response, or malware detection blocks the update.
- Failed scan or validation uploads remain quarantined for administrator follow-up. Validated archives are removed after their contents have been staged. Staging extraction and inspection obey `UPDATE_EXTRACT_TIMEOUT_SECONDS`.
- Archive validation rejects unsafe paths, path collisions, links and special files, encryption, unsupported compression, oversized entries or expansions, excessive file count/depth/path length/compression ratio, and protected state/control paths. A deterministic SHA-256 manifest binds each review callback and production request to the exact staged release.

## Review and activation boundaries

Python syntax checks and the configured rootless Docker test sandbox are required. If isolated tests cannot run, their status is `BLOCKED` and approval is refused. Staging approval, rejection, cancellation, and production approval each verify the administrator, chat, digest, and expiry. Review records are held in memory and expire after 30 minutes; restarting the bot clears active reviews.

Production approval is a distinct action and remains unavailable by default (`UPDATE_DEPLOYMENT_ENABLED=false`). Enabling the temporary upload gate does not enable or authorize deployment. The bot's Unix-socket request submits the exact update, manifest digest, archive digest, fixed `deploy` operation, and callback administrator claim for up to 15 minutes. With the default empty broker allowlist, only a root Unix-socket peer can read a pending request or authorize it. The root-only interactive command displays the full digests and claimed Telegram administrator; the root operator must inspect the actual administrator approval in Telegram, compare the exact candidate, and type the verified ID and full manifest digest.

Optional automatic authorization is controlled only by the root broker's `TELEGRAM_AI_AUTO_DEPLOY_ADMIN_IDS` environment variable. It defaults to empty; malformed values prevent the broker from starting. When explicitly populated, a separate production-approval callback from an ID in that root-owned allowlist can authorize the matching request automatically. The broker binds this one-time authorization to the request's full manifest and archive digests and records `telegram_admin_allowlist_auto_deploy` in its audit trail. This policy does not authorize the upload gate or staging approval alone. It trusts the bot service identity to authenticate Telegram callbacks and report the actual user ID; a compromised bot service account could forge an allowlisted claim. Keep the list minimal and enable this mode only after accepting that trust boundary. Bot-side admin IDs must also allow the same user to use the production callback. Broker state is kept in a root-private SQLite file; authorization is atomically consumed once before the deployment worker starts. Expiry, replay, duplicate requests, digest mismatch, wrong peer, unavailable clock, or unavailable/corrupt state fail closed. Request IDs remain recorded to reject replay; the queue allows at most 20 pending requests and fails closed at 100,000 lifetime records pending operator maintenance. No reusable bearer secret is sent to or stored by the bot process.

The manual operator command is `sudo /usr/local/libexec/telegram-ai-deploy --authorize <UPDATE_ID>`. It requires an interactive root terminal and a working broker socket. The deployment socket remains disabled by default and must not be enabled until target compatibility and staging gates pass. Neither mode independently queries Telegram's update history; manual mode trusts root to verify the actual admin action, while auto mode additionally trusts the bot process and root-owned ID allowlist. A compromised root account or bot service account (when auto mode is enabled) is outside this boundary. The broker also accepts a separate operator-owned enable flag, uses fixed service/release paths, requires root-owned non-writable releases and a protected environment file, and rejects dependency, schema, or control-policy changes. The current broker is designed for `/opt/enan-ultra/current`, `/opt/enan-ultra/releases`, and `telegram-ai.service` running as `enan-ultra`; this has not been matched to the historical Azure target in a live check.

Before activation, the broker verifies the staged request, current source hashes, backup capacity, and an immutable candidate release. It activates by an atomic `current` pointer switch. Health checks require a different active PID and a fresh marker that identifies the active release, an open database, and the same Telegram bot identity. A health failure triggers restoration of the previous verified release. A failed rollback is recorded as `rollback_failed` and requires host-side recovery; a bot notification cannot be guaranteed when the bot itself is unavailable.

Application code is kept separate from `.env`, databases and SQLite WAL/SHM files, uploads, stickers, backups, and runtime state. No database migration or dependency installation is performed. Releases requiring those changes need a separately reviewed procedure and rehearsed recovery plan.

## Security limits

ZIP validation and a malware scan do not establish that uploaded source is trustworthy. Review the exact digest and source changes. Staging approvals are process-local and are not an attestation or signed source identity. The broker's local tests are mocked Windows tests; Linux systemd permissions, ClamAV operation, service restart, and recovery still require disposable Linux staging. Production remains **NO-GO** while the intended host, source provenance, and rollback evidence are unverified.
