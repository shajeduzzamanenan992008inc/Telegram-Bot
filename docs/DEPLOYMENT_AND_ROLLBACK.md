# Telegram ZIP deployment and rollback

> **Production deployment is blocked.** The selected Azure application is `enan-ultra.service`, but its canonical source provenance is unknown and its current home-directory installation is writable by the service account. The local ZIP broker targets a different service/path. Do not enable or install it on that VM.

The Telegram evolution workflow cannot change `/opt/enan-ultra`, invoke systemd, run an arbitrary deployment command, or claim a service restart succeeded. `/evolve_deploy_approve` records the distinct admin decision for an exact patch hash; the configured operator release procedure remains the deployment mechanism.

Telegram `/update` now directly overlays a validated admin ZIP onto the project root and replaces the Python process. It does not use the broker described below and does not provide a service health check or automatic rollback. The separate root-owned broker remains a disabled operator capability for its fixed `/opt/enan-ultra` and `telegram-ai.service` layout; it must not be treated as the path used by `/update`. See [Telegram ZIP updates](./TELEGRAM_ZIP_UPDATES.md) and [update security](./UPDATE_SECURITY.md).

## Broker gates and runtime layout

The broker is disabled by default. Set `UPDATE_DEPLOYMENT_ENABLED=true` and create `/etc/telegram-ai/zip-deploy.enabled` only after verifying all of the following:

- The actual service is `telegram-ai.service`, with `User=enan-ultra`, `WorkingDirectory=/opt/enan-ultra`, and `ExecStart=/opt/enan-ultra/.venv/bin/python -m enan_ultra`.
- The application checkout and app package are root-owned and not group/world writable. The bot may write only its state under `/var/lib/telegram-ai`.
- The systemd unit has `PYTHONPATH=/opt/enan-ultra/src`, so the updated flat-checkout source is the code imported after restart, rather than an unchanged installed wheel.
- `/var/lib/telegram-ai-deploy/{release-backups,deployment-history}` are root-owned mode `0700`; the socket is root:`enan-ultra`, mode `0660`.
- The current runtime health marker matches the active PID and was produced only after DB and Telegram client initialization.
- `/opt/enan-ultra` and `/var/lib/telegram-ai-deploy` have room for activation and a complete verified code snapshot.

The installer copies the broker units/helper but leaves the deployment socket disabled; it does not create the enable flag. Keep the broker socket disabled until an operator has reviewed its host layout and explicitly enables it. If the deployed service uses another account, path, or entry point (as was observed on the supplied Azure VM), the broker intentionally refuses preflight. Reconcile and review that deployment as a separate operator task; do not copy the unit/enable flag blindly.

### Staging-only state-path override

The base unit's working directory is `/opt/enan-ultra`, its writable state path is `/var/lib/telegram-ai`, and the broker expects `/var/lib/telegram-ai/runtime-health.json`. The application's default `DATABASE_PATH=data/telegram_ai.sqlite3` is relative to the working directory; the runtime writes its health marker beside the database. With the base default, that would put both database and marker under `/opt/enan-ultra/data`, outside the unit's writable path, and the marker would not be at the broker's expected location.

For disposable staging only, use the systemd drop-in and state-path environment example under `deploy/staging/`. Build `/etc/telegram-ai/staging.env` from the example configuration using staging-only values, then install the drop-in and `staging-state.env.example` as `/etc/telegram-ai/staging-state.env`. The drop-in clears the base environment-file list and loads the staging configuration followed by the state override, so the absolute staging `DATABASE_PATH` wins. Its parent is the declared writable state root, and the runtime marker then resolves to the broker's expected path. Do not install this staging override on production or copy production environment values into staging.

## Activation, health and recovery

The broker records a journal before activation, takes a non-overlapping lock, securely copies the approved manifest, archive and declared files into a root-private temporary directory, verifies exact hashes there, and confirms live base hashes still match. This prevents staging cleanup or mutation after review from changing the bytes being applied. It snapshots current app source into `/var/lib/telegram-ai-deploy/release-backups`, then atomically replaces each permitted source file. File-by-file switching is used because this deployment is a flat checkout, not a release symlink. An interrupted activation is restored from the verified snapshot when the broker next starts.

The broker restarts only the fixed `telegram-ai.service` and waits up to 90 seconds for a different active PID and a fresh marker for that PID with an open DB, successful `SELECT 1`, and the same Telegram bot identity verified via `getMe`. No customer message or paid AI-provider request is sent for health. A failure after activation restores only the application snapshot and checks the previous release again. `rollback_failed` means recovery was not verified: inspect the protected root-owned deployment journal and service journal, and recover manually from the recorded verified snapshot.

The broker keeps at most five snapshots/500 MiB and never prunes a recovery point automatically; deployment blocks if the existing snapshots plus the projected snapshot exceed either limit. It preflights free space for the snapshot and bounded private release copy. `.env`, databases, uploads, sticker/user data and runtime state are outside the source allowlist and are not copied or modified. Dependencies and database migrations are refused. Releases with those changes need a separately reviewed, backed-up operator procedure; migrations must have their own tested forward/recovery plan.

The broker outcome is delivered to the admin chat after the bot is available again. If both the candidate and rollback fail to start, Telegram notification cannot be delivered by that bot; use root-only `journalctl -u telegram-ai-deploy -u telegram-ai` and `/var/lib/telegram-ai-deploy/deployment-history/` to diagnose it. No live production deployment or recovery drill has been performed by this development change.
