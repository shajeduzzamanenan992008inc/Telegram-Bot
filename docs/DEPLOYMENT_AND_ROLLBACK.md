# Telegram ZIP deployment and rollback

> **Production deployment is NO-GO.** The workspace broker targets `telegram-ai.service` and `/opt/enan-ultra`; the Azure identity and layout described below come from 2026-10-17 operator logs and have not been independently rechecked in this repair. Do not enable or install the broker on that VM based on historical notes.

The Telegram evolution workflow cannot change `/opt/enan-ultra`, invoke systemd, run an arbitrary deployment command, or claim a service restart succeeded. `/evolve_deploy_approve` records the distinct admin decision for an exact patch hash; the configured operator release procedure remains separate from ZIP deployment.

Telegram `/update` authenticates the configured update admin and chat, scans the ZIP, stages a full merged candidate without changing the live tree, runs syntax and rootless sandbox checks, and presents the candidate digest for review. Staging approval does not deploy. A distinct production approval only queues a request through the optional broker, which remains disabled by default. The bot UID cannot authorize activation: a root operator must use the interactive `--authorize UPDATE_ID` command after verifying the exact Telegram approval and full digest. The broker then creates a verified recovery snapshot, builds an immutable source release, atomically switches the `current` symlink, restarts only `telegram-ai.service`, checks health, and attempts rollback if checks fail. Local tests use mocked services; no Linux/systemd or live-host drill has been performed. See [Telegram ZIP updates](./TELEGRAM_ZIP_UPDATES.md) and [update security](./UPDATE_SECURITY.md).

## Broker gates and runtime layout

The broker is disabled by default. Set `UPDATE_DEPLOYMENT_ENABLED=true` and create `/etc/telegram-ai/zip-deploy.enabled` only after verifying all of the following:

- The actual service is `telegram-ai.service`, with `User=Group=enan-ultra`, `WorkingDirectory=/opt/enan-ultra/current`, `PYTHONPATH=/opt/enan-ultra/current/src`, and `ExecStart=/opt/enan-ultra/.venv/bin/python -m enan_ultra`.
- `/opt/enan-ultra` and every release under `/opt/enan-ultra/releases/` are root-controlled and not writable by the bot account. The bot writes runtime data under `/var/lib/telegram-ai`.
- `/etc/telegram-ai/bot.env` is root-owned mode `0600`; the service loads it through `EnvironmentFile`.
- `/var/lib/telegram-ai-deploy/{release-backups,deployment-history}` are root-owned mode `0700`; the socket is root:`enan-ultra`, mode `0660`.
- `/var/lib/telegram-ai-deploy/deployment-authorizations.sqlite3` is created by the root broker in the root-owned mode-`0700` state directory and kept mode `0600`. The bot account must not be able to read or write it.
- The current runtime health marker matches the active PID and was produced only after DB and Telegram client initialization.
- `/opt/enan-ultra` and `/var/lib/telegram-ai-deploy` have room for activation and a complete verified code snapshot.

The installer copies the broker units/helper but leaves the deployment socket disabled; it does not create the enable flag. Keep the broker socket disabled until an operator has reviewed its host layout and explicitly enables it. If the deployed service uses another account, path, or entry point (as was observed on the supplied Azure VM), the broker intentionally refuses preflight. Reconcile and review that deployment as a separate operator task; do not copy the unit/enable flag blindly.

The installer is bootstrap-only. It exits before package/config changes if a versioned `current` release exists or `telegram-ai.service` is active. Do not use it to replace an installed release; use the reviewed, digest-bound broker flow only after all staging gates pass.

### Root operator approval protocol

The Telegram process may create a pending request, but the broker does not accept its claimed administrator ID as proof. Pending requests bind `update_id` (release identifier), full manifest SHA-256, candidate archive SHA-256, operation `deploy`, and a 15-minute expiry. The broker stores these records in a root-private SQLite database and retains consumed/expired IDs to reject replay. At most 20 requests may be pending; after 100,000 lifetime records the broker fails closed and requires operator maintenance. Only a root Unix peer may inspect or consume a request. A root operator runs:

```text
sudo /usr/local/libexec/telegram-ai-deploy --authorize <UPDATE_ID>
```

The interactive command fetches the broker's pending record, displays both full digests and the claimed Telegram administrator ID, asks the operator to verify the actual admin approval in the Telegram admin chat, and requires the verified ID plus the exact full manifest digest. The broker checks the root peer credential, request state, expiry, operation and digest, then consumes the authorization in a serialized SQLite transaction before starting deployment. Duplicate/replayed approvals and changed/stale candidates fail closed. No bearer token or reusable signing key is provided to the Telegram process.

Trust assumption: the root operator independently checks that the configured Telegram admin approved the same update and candidate digest. The broker cannot cryptographically inspect Telegram's polling updates in the current single-process architecture; the manual root review is the separate trusted approval component. Root account compromise or deliberate root-level bypass is out of scope.

### SQLite backup and restore procedure

The application database is SQLite. The broker's release snapshot contains source files only; it does not back up the database or its WAL/SHM sidecars. For staging and any separately approved maintenance plan, use SQLite's online backup API instead of copying a live `.sqlite3` file. The API yields a consistent database snapshot that includes committed WAL content:

```python
import sqlite3

source = sqlite3.connect("/path/to/staging/telegram_ai.sqlite3")
backup = sqlite3.connect("/path/to/staging-backups/telegram_ai.sqlite3")
try:
    source.backup(backup, pages=256, sleep=0.1)
    result = backup.execute("PRAGMA integrity_check").fetchone()
    if result != ("ok",):
        raise RuntimeError("SQLite backup integrity check failed")
finally:
    backup.close()
    source.close()
```

Record the backup SHA-256 and keep it separate from the immutable source snapshot. Rehearse restore only into a separate staging state directory: use the backup API to copy the backup into a fresh staging database, run `PRAGMA integrity_check` and application health checks, then verify expected test records. Never copy a live database file alone while WAL is active, and never restore over production as part of this audit. Production backup location, retention, off-host copy, ownership and restore authority remain target-specific and unverified.

### Staging-only state-path override

The base unit's working directory is `/opt/enan-ultra/current`, its writable state path is `/var/lib/telegram-ai`, and the broker expects `/var/lib/telegram-ai/runtime-health.json`. The Ubuntu installer maps the shipped relative database default to `/var/lib/telegram-ai/telegram_ai.sqlite3`; the runtime health marker is written beside the database. A custom `DATABASE_PATH` must remain under the declared writable state root and must still match the broker's health-marker location.

For disposable staging only, use the systemd drop-in and state-path environment example under `deploy/staging/`. Build `/etc/telegram-ai/staging.env` from the example configuration using staging-only values, then install the drop-in and `staging-state.env.example` as `/etc/telegram-ai/staging-state.env`. The drop-in clears the base environment-file list and loads the staging configuration followed by the state override, so the absolute staging `DATABASE_PATH` wins. Its parent is the declared writable state root, and the runtime marker then resolves to the broker's expected path. Do not install this staging override on production or copy production environment values into staging.

## Activation, health and recovery

The broker records a journal before activation, takes a non-overlapping lock, securely copies the approved manifest, candidate archive, and declared files into a root-private temporary directory, verifies exact hashes there, and confirms current source hashes still match. It creates a verified snapshot under `/var/lib/telegram-ai-deploy/release-backups`, builds an immutable directory under `/opt/enan-ultra/releases/`, then atomically switches `/opt/enan-ultra/current` to that release. It never edits the active release file by file. If activation is interrupted, the broker restores the current pointer from the verified snapshot during recovery.

The broker restarts only the fixed `telegram-ai.service` and waits up to 90 seconds for a different active PID and a fresh marker for that PID with an open DB, successful `SELECT 1`, and the same Telegram bot identity verified via `getMe`. No customer message or paid AI-provider request is sent for health. A failure after activation restores only the application snapshot and checks the previous release again. `rollback_failed` means recovery was not verified: inspect the protected root-owned deployment journal and service journal, and recover manually from the recorded verified snapshot.

The broker keeps at most five snapshots/500 MiB and never prunes a recovery point automatically; deployment blocks if the existing snapshots plus the projected snapshot exceed either limit. It preflights free space for the snapshot and bounded private release copy. `.env`, databases, uploads, sticker/user data and runtime state are outside the source allowlist and are not copied or modified. Dependencies and database migrations are refused. Releases with those changes need a separately reviewed, backed-up operator procedure; migrations must have their own tested forward/recovery plan.

The broker outcome is delivered to the admin chat after the bot is available again. If both the candidate and rollback fail to start, Telegram notification cannot be delivered by that bot; use root-only `journalctl -u telegram-ai-deploy -u telegram-ai` and `/var/lib/telegram-ai-deploy/deployment-history/` to diagnose it. No live production deployment or recovery drill has been performed by this development change.
